Kunjungan Terbatas is available through Protocol Officer -> Booking -> Buat janji temu -> Kunjungan Terbatas. Date/start time are required; only Nama, Instansi, No ID Dinas and Pejabat yang dituju are optional. Protocol manages; assigned PA reads with last-four ID; Super Admin reads full detail without decisions. Reception general responses contain reference/schedule/status, and valid code/QR resolution yields name/last-four ID/target without organization or full ID. Public access and general reports/CSV exclude Terbatas. Synthetic examples `88000090` (Approved) and `88000091` (Pending, assigned to o2) remain; admission depends on the example schedule. VIP creation stays limited to Kepala Otorita. See [KUNJUNGAN-TERBATAS.md](KUNJUNGAN-TERBATAS.md). `npm.cmd run test:preview` starts isolated synthetic servers with fixed clocks; no running app or backend is needed. Date and time entry use shared controls across visitor booking, staff creation, restricted visits and rescheduling: shadcn/ui Calendar/Popover for dates and the ReUI time picker with scrollable hour/minute columns. Both dropdowns have compact spacing, with larger targets on touch screens. See [DATE-PICKERS.md](DATE-PICKERS.md) for sources, behavior and browser verification.

Visitor contact inputs: type only the email username, then choose a complete @domain from one native dropdown. Common providers and @ikn.go.id are listed; Domain lain reveals a domain-only field for other institutional addresses. Pasted/autofilled full addresses are split automatically. Booking and status lookup validate the composed email. Phone accepts only 8–20 digits and preserves leading zeroes; formatted pasted input is cleaned. Controls request appropriate phone keyboards. No contact data is stored as a draft by these controls.

Two independent React/Vite apps and shared UI/data packages. The future backend at `D:/oikn/VMS/backend` has not been created; other repositories are outside this project's implementation scope.

Receptionist scope includes only Approved, Checked in and Checked out, across Dashboard, Today, Booking, counts, search, selected details and code/QR resolution. Pending, Rejected and Cancelled are excluded. Status choices contain the three stored states, derived Terlewat/Missed and All; reception defaults to visit-time sorting and removes stale disallowed status filters. Checked-out visits remain available for history. Check-in requires Approved within the 30-minute-early-through-end window; checkout requires Checked in and is available after the scheduled end, with identity verification and a separate confirmation. The shared query applies a defensive scope, and the synthetic API enforces list/resolve scope. The future backend must enforce the same three-state policy on every relevant list/detail/credential endpoint; frontend filtering is not authorization.

Staff-created appointments: PA and Protocol have Buat janji temu on Dashboard and Booking. PA destinations are assigned non-VIP officers; Protocol destinations are VIP. An explicit create permission is required (production permission mapping: booking.create). The form shares contact, future WITA schedule, named group and optional-document validation, without asking staff to provide visitor consent. Creation starts Pending and opens the new detail for the existing approval step; duration starts at 60 minutes and room/duration are finalized on approval. Creator attribution is staff-only. Failed submissions retain input, duplicate retries reuse a payload-bound key, and closing a filled form offers to continue or discard.

The typed repository.createStaff adapter calls only the synthetic POST /__preview/staff/bookings?role=... route in development. Its request contains officerId/date/time/purpose/name/organization/email/phone/identityType, visitors as the complete name array with the representative first, optional ndName, and idempotencyKey. The preview derives actor, VIP and Pending status, rejects out-of-scope targets and changed-payload key reuse, and strips actor data from visitor lookup. Production must implement the corresponding authenticated staff-create endpoint, database/idempotency and audit persistence, assignment checks and confirmation notifications before wiring the currently unavailable HTTP adapter. No real emails or files are sent by this feature.

Rejection remarks: authorized PA/Protocol staff enter a required public message (5–1000 trimmed characters) and an optional internal note (up to 2000). Staff booking detail shows the two separately. Visitor status and public history receive only the public message; local preview responses exclude the internal note, including create retries, lookup and cancellation. Internal-note reads follow the existing PA/Protocol decision scope; Receptionist and Super Admin do not receive them. Production requires separate backend fields, the same validation/authorization and visitor response allowlists, and notification templates that use only the public message. Real backend persistence and email delivery are not implemented by this frontend preview.

Run from this folder:

```powershell
npm.cmd install
npm.cmd run dev
```

Open `http://localhost:3000/` for visitors and `http://localhost:3000/admin/` for staff. All four preview roles first land at Dashboard; switch roles with the explicitly labeled local preview selector. `127.0.0.1:3000` also works. The internal staff development server uses 3002.

Run `npm.cmd run typecheck`, `npm.cmd test`, and `npm.cmd run build`. With the preview running and Playwright available, `npm.cmd run test:refresh` runs the focused freshness checks; `PLAYWRIGHT_MODULE` may point to a local Playwright module. Each app builds to its own `apps/<app>/dist`. Production hosting must route staff, visitor, asset and future API traffic deliberately; no backend hosting or session configuration has been activated here.

Development data adapter: loopback + development build only. The visitor development server provides `/__preview`; bookings live only in its memory, shared between visitor and staff. Restart resets data. No files are uploaded, no email sent, no real staff account created. Use fictional information. Lookup example: booking `88000002`, email `visitor@example.test`. Reception accepts an 8-digit code, or scans an actual encoded demo QR; every match then requires identity validation and a separate confirmation. Camera uses browser BarcodeDetector with a manual-code fallback and stops on close/unmount. A production QR must be server-issued, scoped and revocable.

Production builds select the HTTP repository and fail explicitly for new workflow operations until backend contracts are implemented. The adapter selection is in `packages/data/src/index.tsx`; implement `httpRepository` against the documented typed interface. Never enable demo adapters or role switching in production. No API URL or identity token is placed in localStorage. Existing staff login/session URLs are retained, but permissions/session response mapping must be reconciled before production use. Server-side authorization and CSRF remain mandatory.
