> Historical audit snapshot. Current implementation, disposition and evidence are in [the 2 November readiness review](PRODUCTION-READINESS-2026-11-02.md) and [verification](../VERIFICATION.md). Older reproductions are not current open findings where the new review records a fix.

## Verdict and decision process

The frontend has useful shared components, schemas, query caching, route splitting and a replaceable repository boundary. It needs narrower feature responsibilities, consolidated policies, accessibility fixes and a typed contract designed from the user's chosen requirements for the new backend. A framework replacement is not justified.

Unavailable production repository methods are expected while this project's backend is unbuilt. They are a planned integration boundary, rather than a defect because they disagree with another repository. Production acceptance remains a later milestone.

For each app-versus-business-requirement gap, ask the user whether to adjust the app or adjust the requirement/plan. Do not silently choose either side. The [decision sheet](D:/oikn/VMS/frontendx/anti-slop/REQUIREMENT-GAPS-2026-10-30.md) names each gap and its alternatives. G01 refresh and G04 reservation behavior were selected for app changes; G02 visitor access was selected for a requirement change. Other gaps remain pending. Historical plan approvals remain context; this follow-up does not authorize all other fixes.

Findings A2-01 through A2-16 below retain their identifiers. Their acceptance paragraphs describe the app-alignment option where a requirement gap exists; they are not a substitute for the user's direction choice. The [refresh implementation note](D:/oikn/VMS/frontendx/anti-slop/STAFF-REFRESH-2026-10-30.md) records the selected change and its verification. Original audit measurements predate that implementation.

## Prioritized findings

### A2-01. MEDIUM: strengthen the frontend contract for the new backend

Rules: R-31, C-4. Architectural preparation; the missing backend is an expected project stage.

The typed repository boundary is a useful starting point. Its inputs/outputs remain too broad: creation uses Partial<Booking>, actions accept arbitrary strings and value bags, lists return complete records and detail selection depends on that complete list. Fixture officer/room data is imported directly into forms. Those choices tie components to the synthetic model and make future pagination or audience-specific responses difficult.

Define explicit create/decision/attendance commands, minimal audience-specific list/detail/public-status responses, bounded list parameters, separate summaries and replaceable reference-data queries. Choose endpoint paths, identifier formats and error envelopes with the new backend; none is inherited from another repository. Keep request details out of components. The production stubs are deliberate, not evidence of a broken existing integration.

Sources: [repository](D:/oikn/VMS/frontendx/packages/data/src/index.tsx:71), [domain/fixtures](D:/oikn/VMS/frontendx/packages/data/src/domain.ts:39).

### A2-03. HIGH: duplicated scheduling rules both reject valid requests and allow invalid attendance

Rules: R-26, C-2, C-4. 30 October disposition: G04 resource scheduling has been corrected in the preview; one shared rule covers approval, rescheduling and approved host changes, and Pending creation does not reserve resources. The original reproduction below is historical. G05 was later selected for app alignment; service-time arrival limits, Missed display and late checkout are verified in preview (RESTRICTED-ARRIVAL-2026-10-30.md). See RESERVATIONS-ACCESS-2026-10-30.md for current evidence.

`CreateAppointment.nextStep()` rejects a request when *any* approved/checked-in appointment overlaps, without comparing the chosen officer or a room. The synthetic staff-create endpoint duplicates the same rule over all bookings. A request for `o3` at 10:00 on 10 December 2099 was blocked because an approved `o2` appointment existed. The browser showed the time error; direct API submission returned 409. No room had been selected and the new request would have been Pending. This also conflicts with the approved rule that Pending requests do not reserve slots.

In the opposite direction, preview approval validates room/duration without the overlap guard used by rescheduling. Preview attendance checks lifecycle state without the approved time window. BR-RSP-03 calls for 30 minutes before start through scheduled end; whether to keep that requirement or change it is decision G05. The current frontend also has no derived Missed view.

Evidence: [form overlap check](D:/oikn/VMS/frontendx/apps/admin/src/features/CreateAppointment.tsx:84), [duplicated preview check](D:/oikn/VMS/frontendx/tooling/preview.ts:185), [API reproduction](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-30/false-conflict-api.json), [browser screenshot](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-30/staff-false-conflict.png), [preview approval](D:/oikn/VMS/frontendx/tooling/preview.ts:376), [frontend eligibility](D:/oikn/VMS/frontendx/packages/data/src/domain.ts:185).

Acceptance: allow overlapping Pending submissions. Centralize one resource-overlap policy for preview approval/rescheduling and test it against the agreed backend behavior: same officer OR same nonempty room, approved/checked-in commitments, adjacent intervals allowed. Enforce the authoritative 30-minute admission boundary through scheduled end; allow overdue checkout after check-in. Test competing approvals and exact clock boundaries. UI hints must not become the authority.

### A2-05. HIGH: HTTP and session failures are handled inconsistently

Rules: R-27, R-39, C-4. New integration/resilience finding.

The shared HTTP wrapper currently expects top-level `message` and `fieldErrors`. The new backend's error envelope has not been defined; establish one explicit contract rather than assuming this shape. Network/timeout failures remain raw errors, and successful JSON is trusted through a type cast. Visitor create displays a general error without mapping server field errors; the staff form has its own mapping logic. Login/logout bypass the wrapper altogether.

A simulated 503 on `/v1/staff/session` redirected the built staff app to login because `Shell` treats every absent session as unauthenticated. Login also labels every non-success response as incorrect credentials, including rate limiting or server failure. These paths need different recovery behavior. A failing visitor refresh correctly retained the previous ticket, which should be preserved.

Evidence: [HTTP wrapper](D:/oikn/VMS/frontendx/packages/data/src/index.tsx:37), [session redirect](D:/oikn/VMS/frontendx/apps/admin/src/main.tsx:123), [login failure handling](D:/oikn/VMS/frontendx/apps/admin/src/main.tsx:282), [flow evidence](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-30/flow-checks.json).

Acceptance: normalize the actual wire error once, including code/field/status/retry information; distinguish offline/timeout, 401, 403, 409, 422, 429 and server errors. Retry session outages without pretending credentials expired; invalidate and clear sensitive cache on real authentication loss. Route field errors back to the correct form step and first invalid control without losing input.

### A2-06. HIGH: staff workspace identity has multiple conflicting sources

Rules: R-26, C-2. Reconfirmed original finding 12 with an additional adapter hazard. **30 October disposition:** G09 now requires one active role per account, superseding the multiple-workspace choice. The production mapper/role-state hazards below remain integration work; the new backend must supply one canonical authenticated role.

Production session mapping uses `request<any>` and picks the first recognized role in the returned array. Reordering roles can therefore change frontend behavior without a deliberate workspace choice. The future backend must enforce the selected authorized workspace, not assume an existing role precedence. The separately exposed `role` state initializes to PA in production and is used by mutation/resolve hooks even when `session.role` was mapped to another role. It currently reaches stubs, but is the wrong foundation for a real adapter.

Evidence: [session mapping and role state](D:/oikn/VMS/frontendx/packages/data/src/index.tsx:133), [mutation role](D:/oikn/VMS/frontendx/packages/data/src/index.tsx:238).

Revised acceptance under G09: one typed authenticated session with one canonical server-assigned active role. Derive hooks from that role, validate permissions server-side on every action, and key/clear caches by identity/role. Administrative reassignment must refresh/invalidate the session and private caches. Do not use role-array order or a preview-role variable to determine production access.

### A2-07. HIGH: public validation and retry semantics differ from the staff path

Rules: R-26, C-2, C-4. Reconfirmed original findings 7 and 8. **30 October disposition:** G06/G07 were selected for app alignment and corrected/verified in preview. See VALIDATION-RETRIES-2026-10-30.md. The reproduction below is historical; production storage/atomicity/delivery remain unbuilt.

Public synthetic creation checks a destination and retry key but does not parse the shared booking schema. Staff creation does. The public attempt map returns an old booking for a reused key without comparing its payload; staff retries compare a normalized payload and reject changed-key reuse. Browser validation does not repair either API contract. These paths make a passing happy-path suite weaker evidence than it appears.

The visitor form generates a new key when edited details change after an uncertain request. The approved resolve-uncertain-attempt and single temporary-failure retry behavior is still absent. This must be resolved before persistent writes and notifications are connected.

Evidence: [public synthetic endpoint](D:/oikn/VMS/frontendx/tooling/preview.ts:222), [staff fingerprint handling](D:/oikn/VMS/frontendx/tooling/preview.ts:172), [visitor attempt handling](D:/oikn/VMS/frontendx/apps/visitor/src/pages/Booking.tsx:183), [schemas](D:/oikn/VMS/frontendx/packages/data/src/validation.ts:23).

Acceptance: explicit create-input schemas with complete roster/active-target/date/contact/supplied-document checks in both adapters. Bind every retry to its normalized payload; distinguish uncertain outcomes from rejected requests. Cover changed payloads, concurrent retries and one logical notification. Keep retry rules in the mutation/data layer rather than repeating them in each form.

### A2-14. MEDIUM: mobile startup performs work before the visitor needs it

Rules: R-40, C-4. New measured performance finding.

The mobile choice screen hides registration with `hidden` but still mounts `<Booking>`. The production network trace loads the booking chunk, validation and date-control wrapper before the visitor chooses registration. The small calendar and QR chunks are deferred correctly, and landing motion respects reduced motion, but the hidden form avoids neither downloads nor initialization.

Lighthouse identified oversized-image savings and delayed discovery of the image from JavaScript. The existing image has dimensions and high fetch priority, which should be retained. No responsive image sources are supplied. The trace also loads approximately 46kB compressed landing-motion code.

Evidence: [hidden form mount](D:/oikn/VMS/frontendx/apps/visitor/src/main.tsx:303), [hero loading](D:/oikn/VMS/frontendx/apps/visitor/src/main.tsx:379), [isolated Lighthouse report](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-30/lighthouse-visitor-mobile-repeat.json).

Preload the existing hero from initial HTML and serve appropriately sized variants of the same approved photograph through `srcset`/`sizes`.
