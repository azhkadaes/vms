## Plan before implementation

- Goal: enforce the existing form rules at public creation, bind each submission reference to normalized input, retry once on temporary transport failure, and resolve an uncertain attempt before accepting another submission.
- Contract: share static wire normalization/roster/privacy/optional-filename validation, then apply current schedule/active-officer checks only to new creation. Replays compare normalized original contents before returning the original record, even if the schedule has since passed. Public input cannot set server-owned identity/status/history/actor fields.
- Recovery: a typed resolve operation accepts the unpredictable submission reference and original email. It returns the permitted original booking or conclusively closes a missing reference. Closing prevents a delayed original POST from creating a booking after a not-committed answer. A completed result never automatically sends edited details. A not-committed result retains the current form and requires explicit review/send again. The future backend must implement these operations atomically.
- State: RHF owns the draft, a small submission controller owns the pending reference and transport phases, and the component renders those phases. Store only the pending random reference in sessionStorage before sending; no draft, contact, document or payload is persisted. This allows recovery after reload without implementing G14 draft storage. Original email is retained in memory during the attempt and requested again after reload. Clear the reference only after confirmed success, definitive rejection or conclusive recovery.
- Components: retain the existing booking steps/controls and add a focused recovery panel with localized text, original-email input and explicit resolution action. Server field errors return to the owning step/field without resetting input. Prevent native step-navigation submission and repeated in-flight sends. Keep existing UI style and motion; no new assets.
- States: sending, one automatic retry, received, definite field/access/conflict failure, uncertain result, checking result, confirmed absent, wrong recovery email and unavailable session storage. Recovery can run even when the edited draft is invalid. Announce retry/recovery status and focus result/error/field feedback.
- Three performance questions: reuse existing schemas; perform no extra request on successful submission; resolve only uncertain attempts and validate authoritatively in the service. No polling, worker or new dependency. Keep the controller independent of React so failure sequences can be tested deterministically.
- Tests: normalized replay, changed replay, concurrent identical POSTs, complete field/roster/consent/active-officer validation, derived server fields, lost response after commit, one retry limit, no retry on HTTP validation/access/conflicts, sealed missing references and delayed POST, recovery after edits/reload, field error focus/input retention, keyboard and narrow screens. Run existing policy/API/browser regressions, typecheck and both builds.
- Limits: preview file validation is filename metadata plus existing client MIME/size checks; real upload validation/storage stays future work. No real notification is sent. Production idempotency/recovery lifetime and submitted-record retention remain unselected; the synthetic service retains attempts only for its process lifetime.

## Implementation and backend handoff

- `validation.ts` shares normalized public input with the form/service. It validates consent, the complete roster with representative first, known identity type, current contact/name/purpose limits and optional filename. New creation additionally checks service time, valid calendar/office hours and active destination. Replays normalize without applying newly elapsed time/inactive-target checks, then compare the original contents. Server-owned fields are derived from parsed allowlisted input.
- `submission.ts` owns phases/reference and one automatic transport retry, separately from React. The form remains its draft owner and `SubmissionRecovery` renders recovery. The repository adds typed `resolveSubmission`; the HTTP adapter remains unavailable pending the new backend.
- The service's POST `/__preview/submissions/resolve` accepts `{idempotencyKey,email}`. It returns `{outcome:"committed",booking}` using the public projection, or `{outcome:"not_committed"}` after closing that missing reference. Wrong original email returns 401 without a booking. Late POSTs to closed references return 409. The new backend needs durable atomic equivalents, not process-memory maps.
- After a lost first response, a rejection of the retry cannot erase the original uncertainty. Validation/access/conflict/rate-limit replies on a first attempt are not automatically retried. Ambiguous server/malformed-success outcomes retain recovery; only TypeError transport failures and network/timeout errors trigger the single automatic retry.
- Only the random pending reference is stored in the tab's sessionStorage, before sending. No draft/contact/roster/document/response is persisted. Reload asks again for the original email. The reference is cleared after a receipt is displayed, a definite first-attempt rejection, or conclusive missing recovery. An unmounted/retired form cannot remove a newer form's reference. This does not implement G14 draft recovery or establish a production idempotency lifetime.
- Recovery of a completed request shows the original receipt and current lifecycle wording, including when a decision happened meanwhile. Recovery of a missing request preserves the current form and requires another explicit reviewed submission. Server field errors return to their step/control without clearing other input. Moving into review sends no request.
