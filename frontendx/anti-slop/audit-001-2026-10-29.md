# VMS UI, flow, code and readiness audit

> Historical audit snapshot. Current implementation, disposition and evidence are in [the 2 November readiness review](PRODUCTION-READINESS-2026-11-02.md) and [verification](../VERIFICATION.md). Older reproductions are not current open findings where the new review records a fix.

Audit date: 29 October 2026, Asia/Makassar. Mode: audit first, selected by the user. No application source was edited. Build outputs, audit evidence and temporary validation caches were generated. Existing backend changes were preserved.

Subsequent user review: decisions for all 16 findings were individually approved, including a 30-minute early check-in allowance with late arrival allowed through the scheduled end. [IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md) records the approved scope and acceptance checks. The audit below remains historical evidence; this planning update does not close any finding.

The integration suite and browser walkthrough added fictional QA records to the already-running development preview's memory. They disappear on its next normal restart. That preview was not reset or stopped, preserving its existing state. The separate adversarial preview on port 3300 and built-visitor smoke server on port 4170 were stopped after the audit.

**Verdict: do not sign off for production.** The preview has a coherent institutional identity and several working flows, but its production adapter is unavailable, revised privacy requirements remain unimplemented, and the audit reproduced operational and responsive defects. Passing builds and tests establish a useful baseline, not live readiness.

The review covers the active `D:/oikn/VMS/frontendx` visitor and staff apps, shared UI/data packages, development API, tests and product/design documents. The separate Go checkout was inspected for contract alignment and tested. The legacy `D:/oikn/VMS-FE` app was used only as background, not audited as a second deliverable. `frontendx` currently has no Git repository metadata, so a frontend Git diff was unavailable.

## Prioritized findings

The numbers below are approval identifiers. HIGH identifies failed functional, privacy, resilience or accessibility gates. LOW identifies copy/design consistency work. Planned integration work is identified explicitly rather than represented as a newly introduced regression.

### 1. HIGH: production builds cannot perform the core visit workflow

Rules: R-26, R-35, C-2. Classification: known release blocker, confirmed again.

All six methods of `httpRepository` call `unavailable()`: listing, public creation, staff creation, actions, reception resolution and visitor lookup. In the built visitor app served on port 4170, submitting a valid lookup produced the technical message about connecting the HTTP adapter. There was no preview notice in that production build.

The missing adapter also conceals real contract differences: Go still uses visitor challenge/verification and reschedule proposals; the frontend expects pair lookup and fixed rescheduling. Go Receptionist list scope omits `checked_out`, while the frontend includes it. Staff creation, roster/document persistence and the minimized ordinary-visit identity policy also require reconciliation. Hardcoded officer/room identifiers remain frontend fixtures.

Evidence: [adapter](D:/oikn/VMS/frontendx/packages/data/src/index.tsx:109), [Go visitor routes](C:/Users/ASUS/go/src/github.com/thdoikn/VMS-BE/internal/server/rest/router/visitor_access_router.go:15), [Go reschedule route](C:/Users/ASUS/go/src/github.com/thdoikn/VMS-BE/internal/server/rest/router/staff_booking_router.go:35), [Go reception scope](C:/Users/ASUS/go/src/github.com/thdoikn/VMS-BE/internal/repository/staff_booking/implementation/repository.go:39), [production screenshot](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/production-status-unavailable-390.jpg).

Acceptance: an agreed, authenticated backend contract supports a complete visitor submission, authorized staff decision, visitor status, attendance and notification flow. Contract tests must exercise the actual adapter and response projections. Hide or explain unavailable capabilities in product language until then.

### 2. HIGH: cancellation and QR access still use the older visitor proof model

Rules: R-26, R-35, C-2. Classification: planned requirement not implemented.

The latest plan allows email plus code to show limited status, but requires a signed email link or equivalent email-possession proof for cancellation and QR access. The current preview cancels using only code, email and version. An approved lookup automatically renders its demo QR without the stronger proof step. The synthetic integration tests confirm the older pair-based cancellation contract rather than the revised requirement.

Evidence: [current requirement](D:/oikn/VMS/frontendx/PLAN.md:31), [cancellation](D:/oikn/VMS/frontendx/apps/visitor/src/pages/Status.tsx:236), [ticket](D:/oikn/VMS/frontendx/apps/visitor/src/features/VisitTicket.tsx:75). Browser lookup showed the approved demo QR; pending lookup correctly omitted it.

Acceptance: keep the no-OTP interface, distinguish limited status access from verified actions in the typed contract, and enforce the stronger proof on the server. Demo QR generation must remain explicitly synthetic. This audit did not demonstrate a public production vulnerability: the production operations are currently unavailable.

### 3. HIGH: Terbatas still follows the superseded privacy/access contract

Rules: R-26, R-35, C-2. Classification: planned requirement not implemented; current privacy behavior reproduced with synthetic data.

The revised contract requires the four optional fields Nama, Instansi, No ID Dinas and target pejabat; assigned PA and Super Admin read access; redacted Receptionist general views; credential-gated identity details; and exclusion from general exports. Current code instead:

- Excludes every restricted visit from PA and Super Admin scope.
- Has no No ID Dinas field and retains the older email, phone, purpose, identity type, roster and document fields.
- Returns the restricted name, organization, host and roster to Receptionist list requests before credential resolution.
- Includes all scoped records in general CSV generation, including Terbatas for Protocol.
- Still tells users that only Protocol and Receptionist can access the record.

An isolated probe created and approved a restricted record. A normal Receptionist list returned `Audit Restricted Person`, `Audit Private Org`, its target and roster without a code/QR. Assigned PA and Super Admin lists returned no matching record. No real personal data was used.

Evidence: [requirements](D:/oikn/VMS/frontendx/KUNJUNGAN-TERBATAS.md:9), [scope](D:/oikn/VMS/frontendx/packages/data/src/domain.ts:102), [projection](D:/oikn/VMS/frontendx/packages/data/src/domain.ts:170), [form](D:/oikn/VMS/frontendx/apps/admin/src/features/RestrictedAppointment.tsx:96), [CSV](D:/oikn/VMS/frontendx/apps/admin/src/pages/Settings.tsx:57), [probe result](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/restricted-projection.json).

Acceptance: implement the revised role projections before search, counts, pagination, direct IDs and export; verify assignment changes, blank hosts, masked IDs and credential-gated reception detail. Update tests that currently assert the superseded exclusions.

### 4. HIGH: staff lists can miss new requests indefinitely

Rules: R-27, R-35, C-4. Classification: reproduced preview defect with the same cache policy used in production.

The shared query disables window-focus refetch, provides no polling or subscription, and exposes no normal refresh action on the staff list. Thirty seconds of `staleTime` does not initiate a refresh. Mutations invalidate the cache only in their own tab.

Reproduction: keep the PA appointment list open, submit `Audit Synthetic Visitor` from a different visitor tab, and search for that name. The staff list still showed 14 records and no match. Reloading showed 15 records and the new request. This is operationally significant for staff waiting for arrivals or decisions.

Evidence: [query policy](D:/oikn/VMS/frontendx/packages/data/src/index.tsx:25), [booking hook](D:/oikn/VMS/frontendx/packages/data/src/index.tsx:215), [before reload](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/staff-stale-search-320.jpg), [after reload](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/staff-after-reload-320.jpg).

Acceptance: choose a bounded refresh/subscription strategy, provide a visible manual refresh and freshness/error indication, and verify cross-tab/cross-user updates without a full-page reload.

### 5. HIGH: the preview can approve conflicting visits

Rules: R-26, R-35, C-2. Classification: reproduced synthetic API defect, not a demonstrated Go defect.

Rescheduling checks host/room overlap, but approval only validates the room and duration before changing status. Two pending public requests for the same officer, date, 10:00 start and 60-minute duration were both approved into Ruang Rapat Nusantara. Both approval requests returned 200. The real Go approval repository does contain a conflict check, so this preview gives weaker evidence than the real intended operation.

Evidence: [preview approval](D:/oikn/VMS/frontendx/tooling/preview.ts:376), [state change](D:/oikn/VMS/frontendx/tooling/preview.ts:442), [probe results](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/api-probes.json).

Acceptance: apply the same host/room interval policy on approval and rescheduling, with conflicts checked against current authoritative state. Cover simultaneous approvals and conflicting duration changes.

### 6. HIGH: the preview permits attendance outside the visit window

Rules: R-26, R-35, C-2. Classification: reproduced synthetic API defect.

`can()` checks role and lifecycle state but no visit time. The preview mutation applies no time-window check. A visit scheduled for 30 October 2099 was checked in during this 29 October 2026 audit and returned 200 with `checked_in`. The browser also resolved tomorrow's newly approved visit into the normal identity confirmation screen.

Evidence: [action eligibility](D:/oikn/VMS/frontendx/packages/data/src/domain.ts:190), [preview attendance](D:/oikn/VMS/frontendx/tooling/preview.ts:450), [probe results](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/api-probes.json).

Acceptance: represent and enforce the agreed admission window in the preview contract and actual server, including expired visits, clock boundaries and repeat scans. Preserve manual identity validation and explicit attendance confirmation.

### 7. HIGH: public preview creation bypasses its own validation contract

Rules: R-26, R-35, C-2. Classification: reproduced synthetic API defect.

Staff creation parses a schema; public creation does not. A public request containing a one-character name, invalid email, date `1900-01-01`, time `99:99` and an empty roster returned 201. The client form rejects these values, so the current happy-path suite cannot establish server validation parity. Malformed accepted records can also break downstream formatting/components that assume valid data.

Evidence: [public create](D:/oikn/VMS/frontendx/tooling/preview.ts:223), [shared schemas](D:/oikn/VMS/frontendx/packages/data/src/validation.ts:23), [probe results](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/api-probes.json).

Acceptance: parse the public request with a complete server input schema, validate roster invariants and supplied document metadata, and return safe field errors. Do not rely on browser validation as enforcement.

### 8. HIGH: public submission idempotency does not bind the payload

Rules: R-26, R-35, C-2. Classification: reproduced synthetic API defect.

The public attempt map stores a booking by key without a request fingerprint. Reusing an existing key with a changed name/roster returned 201 and the original person's booking. Staff creation correctly rejects changed-payload reuse with 409, so the two create paths behave differently. The visitor UI normally changes its key when the payload changes; that does not repair the endpoint contract.

Evidence: [public retry](D:/oikn/VMS/frontendx/tooling/preview.ts:229), [staff retry](D:/oikn/VMS/frontendx/tooling/preview.ts:172), [probe results](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/api-probes.json).

Acceptance: compare a normalized request fingerprint for every replay, reject changed-payload reuse, and cover concurrent retries and public response allowlisting.

### 9. HIGH: the installed dependency set has an unresolved Zod advisory

Rules: C-4, C-5; dependency/readiness check. Classification: dependency finding, exploitability not demonstrated.

`npm audit` reported one high-severity advisory against installed Zod 3.25.76: GHSA-mrhx-c7xc-m3w5, uncontrolled resource consumption during collection validation. The current advisory lists versions below 4.6.6 as affected. The preview has a request-body size limit and many array constraints; this audit did not establish whether an exploitable input reaches the vulnerable path here. The advisory remains unresolved rather than dismissed because a build passed.

Evidence: [manifest](D:/oikn/VMS/frontendx/package.json:27), [GitHub advisory](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5). No automatic dependency update was applied. The suggested npm fix crosses a major version.

Acceptance: assess the reachable paths, select a patched compatible dependency strategy, retain body/collection bounds, and rerun resolver, schema, integration and build checks. Do not apply an unreviewed forced major upgrade.

### 10. HIGH: the employee page breaks at 320px

Rules: R-03, C-4. Classification: reproduced UI defect.

At 320x740, the page introduction retains a horizontal heading/button layout. The add button reached x=362, outside the viewport. Focusing the directory search scrolled the page horizontally, shifting the panel heading and hint off the left edge. The employee table's internal horizontal scroll is a valid strategy; the page-wide overflow is the defect. The settled 390px check measured a 390px document width, and the 768px check did not show page-wide overflow after layout settled.

Evidence: [page introduction styles](D:/oikn/VMS/frontendx/apps/admin/src/styles.css:277), [mobile override](D:/oikn/VMS/frontendx/apps/admin/src/styles.css:984), [directory heading styles](D:/oikn/VMS/frontendx/packages/ui/src/styles.css:441), [320px screenshot](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/employees-empty-320.jpg).

Acceptance: stack or wrap the introduction and directory controls at narrow widths, keep the table within its own scroll container, and verify no document overflow before and after field focus at 320px and 200% zoom.

### 11. HIGH: reporting treats absent or failed data as zero

Rules: R-27, R-36, C-5. Classification: preview reporting defect and production integration gap.

Settings obtains `useBookings()` and immediately uses `q.data || []`, without loading/error/retry handling. Super Admin has reporting permissions but deliberately has no ordinary booking scope, so its analytics screen displays six zero totals and offers a header-only CSV despite visits existing. For an operational role, a failed list request also becomes empty analytics/history rather than an error. General audit reporting is reconstructed from booking histories, not an independent audit/reporting source.

Evidence: [records fallback](D:/oikn/VMS/frontendx/apps/admin/src/pages/Settings.tsx:51), [scope](D:/oikn/VMS/frontendx/packages/data/src/domain.ts:104), [Super Admin analytics](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/superadmin-analytics-desktop.jpg).

Acceptance: use a reporting contract with explicit aggregate/report permissions, exclude Terbatas from general exports, distinguish unavailable/forbidden/empty/failed data, and disable export while its source is unresolved. Do not grant broad booking access merely to populate the chart.

### 12. HIGH: production multi-role sessions can disagree with backend scope

Rules: R-26, C-2. Classification: source-confirmed integration defect; real multi-role login not exercised.

The frontend takes the first supported role returned in the session array. The backend selects visit scope by explicit precedence: Protocol, then PA, then Receptionist. An employee with roles ordered Super Admin then PA can therefore receive a configuration-only frontend and empty client scope while the backend permits PA work. The single-role preview selector cannot test this condition.

Evidence: [frontend role selection](D:/oikn/VMS/frontendx/packages/data/src/index.tsx:148), [backend scope resolution](C:/Users/ASUS/go/src/github.com/thdoikn/VMS-BE/internal/usecase/staff_booking/staff_booking_usecase.go:43).

Acceptance: agree how combined roles are represented, resolve role capabilities consistently, and test reordered/multiple role arrays against the actual session adapter without expanding unauthorized access.

### 13. HIGH: employee search has no zero-result state

Rules: R-27. Classification: reproduced UI state defect.

Searching `NoSuchAuditPerson` leaves a bare table header and the generic demo hint. There is no no-match message, result announcement or reset action, although the appointment list has a useful zero-result state.

Evidence: [employee filtering](D:/oikn/VMS/frontendx/apps/admin/src/pages/Settings.tsx:121), [empty search screenshot](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/employees-empty-320.jpg).

Acceptance: provide a clear no-match message and reset search action, including an accessible result update. Keep the normal empty directory distinct from filtered zero results.

### 14. LOW: phone navigation does not match the latest approved direction

Rules: R-20, R-31. Classification: design/implementation mismatch.

The 29 October design calls for status/registration actions in the phone navbar, with the current dedicated task omitted and a shortened registration label when needed. The component renders the entire navigation only when `!mobile`. On the 390px status page, the header contains the Home logo and language selector but no registration shortcut. Visitors must return Home to choose the other task. The older segmented language controls also remain in the mobile hero/task surfaces, while the latest direction describes a single native ID/EN selector.

Evidence: [direction](D:/oikn/VMS/frontendx/DESIGN.md:157), [conditional navigation](D:/oikn/VMS/frontendx/apps/visitor/src/main.tsx:109), [mobile production screenshot](D:/oikn/VMS/frontendx/anti-slop/evidence-2026-10-29/production-status-unavailable-390.jpg).

Acceptance: reconcile the shell with the latest direction at 320px/390px, preserving the selected task's scroll lock, Back behavior and accessible names. Avoid adding redundant simultaneous controls.

### 15. LOW: visitor history exposes internal event wording and mixed languages

Rules: R-16, C-1. Classification: reproduced copy/data presentation defect.

After switching the visitor status page to English, the surrounding interface translated, but the timeline still showed `Permohonan diterima` and `PA: approve`. These are stored display strings, including role/action vocabulary, rather than localized visitor-facing event descriptions.

Evidence: [history rendering](D:/oikn/VMS/frontendx/apps/visitor/src/pages/Status.tsx:115), [preview history construction](D:/oikn/VMS/frontendx/tooling/preview.ts:459). The approved synthetic visit was used for this check.

Acceptance: represent history as typed events plus safe public metadata, render natural localized visitor descriptions, and keep staff/internal notes outside public history.

### 16. HIGH: visitor heading structure skips the active page level

Rules: R-39. Classification: confirmed semantic accessibility defect; visual impact is small.

The standalone status page has an h1 followed by the ticket person's h3, with no intervening h2. In the selected mobile registration surface, the visible form starts at h2 after the landing introduction is hidden. These structures make heading navigation less reliable for people using assistive technology even though the screens look orderly.

Evidence: [ticket name heading](D:/oikn/VMS/frontendx/apps/visitor/src/features/VisitTicket.tsx:42), [embedded heading selection](D:/oikn/VMS/frontendx/apps/visitor/src/pages/Booking.tsx:53). The browser accessibility trees confirmed these levels.

Acceptance: give the active page/task a consistent h1 and keep subordinate headings in order; preserve the established visual styling independently of HTML heading level. Verify both embedded and dedicated routes.
