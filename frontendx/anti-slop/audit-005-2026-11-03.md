3 November 2026, WITA. Scope: D:/oikn/VMS/frontendx. Accessibility skill plus frontend-engineering review. Antislop mode: after, explicitly selected in this chat. Application source was not changed; this deliverable contains audit scripts, evidence and this report. Builds regenerated dist output. **Verdict: hold production release.** Both builds and all 191 existing tests pass when browser checks run on isolated ports, but the aggregate check fails formatting and additional rendered states expose accessibility defects. Real-service and deployment acceptance also remain open. Passing a landing-page Lighthouse score does not establish WCAG conformance across the application.

## Current direction and audit approach

Retain the OIKN identity, neutral staff surfaces, existing typography, semantic tokens and operational flows in DESIGN.md. No redesign, new visual asset or dependency is proposed. All additional work runs locally; no production data, submission or deployment was involved.

## Findings for selection

1. **HIGH: shared email controls do not preserve visible names or keyboard focus.** Source: packages/ui/src/index.tsx:110 and :142. On /status, choose an organization/custom domain or paste test@example.test. The visible button is `Ubah`, but its accessible name is `Pilih domain dari daftar`; axe reports the serious `label-content-name-mismatch` violation. The email input's visible `Email pendaftaran` label is also overridden by `Nama email sebelum @`, confirmed in the rendered accessibility tree, although axe does not flag that external-label mismatch. The shared staff email input has the same override. Focusing the custom-domain button and pressing Enter replaces it with the domain selector and leaves focus on BODY rather than the replacement control. This is a recoverable focus loss, not a demonstrated keyboard trap. Fix: include the visible button text in its accessible name, preserve the contextual email label with a supplemental part description, and focus the domain selector after the switch; verify the opposite switch too. Recheck ID/EN, lookup and registration/staff forms. WCAG 2.5.3; antislop R-39 and R-32. Evidence: evidence-2026-11-03/status-error.axe.json, status-error.tree.txt, status-error.png, manual-results.json entry email-return-to-list-focus. The action itself works; the naming and continuity need correction.

2. **HIGH hard-gate priority: open mobile navigation combines incompatible HTML/ARIA semantics.** Source: apps/admin/src/main.tsx:490–515 and apps/admin/src/components/lightswind/sidebar.tsx:43. At 390px, activate `Buka navigasi`. Radix Dialog.Content uses asChild on SidebarRoot, which renders an aside; the result is `<aside role="dialog">`. Axe reports `aria-allowed-role` (tool impact: minor). Fix: use a valid neutral dialog container while retaining the desktop aside landmark and existing drawer styling, title/description and focus management. Re-run axe with the drawer open and exercise Tab, Shift+Tab and Escape. Escape currently closes it and returns focus to Buka navigasi; no trapped or blocked navigation was established. The HIGH gate priority follows antislop R-39's prohibition of ARIA contradicting native roles, not a claim of critical user impact or a demonstrated WCAG 4.1.2 failure. Evidence: evidence-2026-11-03/staff-mobile-menu.axe.json, staff-mobile-menu.tree.txt and staff-mobile-menu.png.

3. **MEDIUM: the documented release check is red.** `npm.cmd run check` stops at its first step: Prettier reports apps/admin/src/styles.css and apps/visitor/src/styles.css. This is formatting, not a failed runtime build. Fix: format the two stylesheets, verify the diff preserves declarations, then run the aggregate check. The standard browser runner also encountered an occupied 3002 port in this session; that environmental condition is not an application defect. All 50 preview browser tests passed using fresh servers on 3130/3132. Engineering verification gate; R-35 requires an honest check result. Evidence: evidence-2026-11-03/check.log, check-results.json and isolated-browser.log. Do not retain the PLAN.md:30 assertion that current formatting passes without a successful new run.

4. **MEDIUM, existing acceptance gap: mobile performance remains below the project's provisional target.** Fresh Lighthouse 12.8.2 mobile navigation against the built visitor landing page: performance 85, accessibility 100, best practices 100; FCP 2.56 s, LCP 3.77 s, total blocking time 31 ms, CLS 0. This one local sample is consistent with the previous documented mobile median, not evidence of a regression. The provisional 90 performance / 2.5 s LCP target remains unmet on this uncompressed fixture host. Fix/acceptance: verify Brotli/gzip and caching on the intended host, measure again, then address remaining measured render-blocking resources if needed. Do not infer deployed or field performance from this run. Engineering performance gate; R-40 requires measured claims and is not itself failed merely by this score. Evidence: evidence-2026-11-03/lighthouse-mobile.json, lighthouse-mobile.html and lighthouse.log; existing target in VISITOR-CRITICAL-REQUESTS.md.

Recommended first implementation selection: **1–3**. Item 4 needs a deployment measurement before selecting further performance changes. After-mode fixes await explicit selection; no application fixes were applied in this audit.
