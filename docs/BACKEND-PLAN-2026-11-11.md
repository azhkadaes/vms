## 3. Architecture and folder structure

```text
backend/
  cmd/main.go                         # API entry point, matching reference
  cmd/worker/main.go                  # same application, background entry point
  cmd/migrate/main.go                 # explicit migration command, never API auto-migration
  config/
  internal/
    entity/                          # business records/value types; no Fiber imports
    entity/base/
    handler/                         # parse HTTP, call use case, serialize/map status
    usecase/<capability>/             # interface and application input/result types
    usecase/<capability>/implementation/
    repository/<capability>/          # persistence interfaces, no Fiber types
    repository/<capability>/implementation/
    serializer/<audience>/            # explicit output/projection interfaces
    serializer/<audience>/implementation/
    policy/                          # centralized role/action/record/field decisions
    server/rest/{router,middleware}/
    worker/                          # claiming, delivery/retry, cleanup lifecycle
    infrastructure/{mail,storage}/    # concrete external adapters
  pkg/dto/                           # HTTP request/response shapes, reference convention
  pkg/helper/                        # only genuinely shared, cohesive utilities
  migration/files/                   # reviewed versioned SQL
  docs/                              # implementation architecture/spec/evidence later
```

Capabilities: identity/access, visits/scheduling, reception/admission, documents, directory/catalogs, administration, reporting, notifications/audit. These are logical ownership boundaries across the selected layer folders, not a service or repository per database table. A use case may coordinate several repositories through one transaction boundary.

Dependency rules:

1. Router composition constructs implementations and injects their interfaces. Avoid service locators or package-global DB/config state.
2. Handlers depend on use-case/serializer interfaces. Business rules never depend on Fiber, HTTP status codes or response envelopes.
3. Use cases return application results and typed business errors. They depend on repository/policy/transaction/provider contracts, never concrete GORM handles.
4. Repository implementations use GORM and parameterized SQL; persistence queries may return bounded read projections. No arbitrary cross-capability table mutation.
5. Serializers map already-authorized data to explicit audience DTOs. They must not become a second business-rule engine or expose the entity by default.
6. API and worker reuse the same application operations. Notification delivery never changes a visit decision merely because email failed.
7. Preserve interface/implementation pairs chosen in D11; split large interfaces by actual callers and responsibilities. DTOs remain ordinary data structures.

SOLID: handlers, policies, commands, persistence, projection and delivery each own one concern; provider variation uses narrow interfaces; implementations preserve documented error/cancellation behavior; dependencies are injected. Do not add a generic CRUD framework, event bus, cache, broker or microservice without a demonstrated requirement and a new choice.

## 6. Transactions, concurrency and request recovery

Representative approval operation:

```text
parse bounded request and authenticated principal
begin transaction with explicit deadline
  validate current authority; coordinate role/account revisions with admin writes
  lock visit; compare requested version and allowed state
  determine old/new non-null resources
  lock official rows and room rows in documented type/ID order
  recheck active references and overlap after resource locks are acquired
  update visit conditionally; increment version
  revoke incompatible admission credentials
  append filtered audit and uniquely identified notification intent
commit
return authorized updated projection; email delivery follows in worker
```

Define one global locking protocol including principal/policy rows, visits, resources and credentials. Scheduling operations lock the visit before old/new resource rows; all resources use the same type/ID order. Creates have no existing visit row. Resource locks precede the overlap query under Read Committed so a waiting transaction sees the previous winner's committed reservation. Do not rely on a Repeatable Read snapshot created before waiting. All approval, staff creation, reschedule, target/room/duration changes, cancellation and attendance state transitions use the protocol. Test deadlock handling and bounded retries; never retry validation or business conflicts automatically.

Overlap uses full timestamp intervals `[start,end)` and assigned officer OR assigned room; nulls reserve nothing. Do not copy the preview's same-date-only comparison as database logic. New/old resource changes acquire both sets of locks. Two pending visits can overlap; two approvals cannot. No SMTP call occurs while holding database locks.

Use-case transaction interface supplies transaction-bound repository interfaces; concrete implementation opens one GORM transaction and passes `tx` to all writes. Never mix `db` and `tx` or smuggle an untyped transaction through context values. Database constraints backstop valid statuses, positive durations/versions, FKs, unique codes, request references and attendance transitions.

Creation: durably scope idempotency by audience and principal/reference; bind normalized payload and eligible file linkage. Same key/same payload resolves to the original booking, serialized under current authorization and field visibility; changed payload returns 409. D22 retains committed reference/outcome linkage for as long as the associated visit is retained. Do not replay a cached private response after authority changes or append another logical notification. Public resolution and creation serialize on the same durable request record, including when it does not yet exist, using a unique insertion/upsert protocol. A not-committed resolution closes the key against late creates. Retain minimal closure state rather than an unnecessary uncommitted visitor payload. Future retention/purge design must not make a previously closed or purged key look unused and allow a delayed duplicate create; no automatic closure-marker deletion is authorized by D22. Restart/timeout never means a rollback is assumed. Staff retries use the same create reference; no extra staff recovery endpoint is necessary merely to replay a committed create.

Other commands: expected version and state prevent duplicate transitions/audit. A lost response followed by stale-version conflict requires an authorized reload. Do not silently auto-repeat a different user decision. Admission replacement and consumption lock the relevant visit/credential state. Concurrent role switches must not authorize a request under a different role than the one it was validated against; revalidate revision within the write transaction and fail safely if authority changed.

## 7. Worker and external operations

Run API and worker as separate processes/containers from the same repository and release. Start with PostgreSQL-backed outbox; no external message broker. API success means the business change and job are saved, not that email has arrived.

- Claim a bounded batch with row locking/`SKIP LOCKED`, assign lease/owner and commit the claim quickly.
- Send outside the claim transaction with explicit provider timeout. Record completion only if the lease still belongs to this worker; heartbeat/reclaim avoids overlapping active attempts where practical.
- Retry temporary failures with bounded backoff/jitter for up to 24 hours from the first failed delivery attempt (D23); record that deadline durably, including across restarts, and do not start another automatic attempt after it. D36 selects waits after successive failed attempts of 1 minute, 5 minutes, 15 minutes, 1 hour, 3 hours and then 6 hours repeatedly. Add small bounded timing jitter; if the resulting next attempt would fall after the deadline, stop and flag for review rather than moving the deadline. Persist attempt number and next-attempt time so restart does not reset the schedule. Respect a provider's longer retry delay without violating the deadline. Stop permanent failures earlier and surface them in operational diagnostics. A failure remains visible for reviewed recovery; it is not silently deleted or reset by restarting the worker. Preserve per-visit event ordering or suppress obsolete notification work according to reviewed semantics; revalidate freshness before a delayed send. Provider throughput/concurrency configuration must be checked for the selected provider.
- Use a unique logical event key and stable message identity. SMTP acceptance followed by a crash can cause uncertain delivery; do not promise exactly-once email. Separate logical deduplication from provider delivery guarantees.
- Reclaim expired leases after restart; shut down by stopping new claims and allowing a bounded drain. Database connection budgets include API and worker pools.
- Clean only expired unlinked uploads through an atomic state transition shared with linking. Never delete a just-linked file. Submitted-data retention/deletion requires organizational policy, not an invented cleanup interval.
- No recipient/token/file content in logs; no live email during disposable tests. Worker backlog age, retries, failures and heartbeat must be observable.

Initial workload volumes/concurrency/availability targets are unknown. Begin with bounded queries and controlled worker concurrency. Scale HTTP instances and job concurrency independently only after measuring latency, queue age, DB contention and provider rate limits. Additional workers do not remove shared-DB or SMTP bottlenecks.

## 13. Authentication implementation requirements

This version exposes local login only. Keep credential verification separate from session issuance, employee lookup, role selection and permission checks, using the existing selected layers and constructor injection. Authentication returns a verified internal employee identity; the shared session service owns JWT issuance, refresh rotation, expiry and revocation. Business use cases depend on current VMS authority rather than password checks or provider-specific claims. This keeps the selected browser contract reusable for a later identity-provider adapter without building an unused provider framework.

SSO is deferred: no current SSO routes, login buttons, provider configuration, speculative identity-link tables or protocol dependencies. Confirm the actual organization provider/protocol before later schema/API design. At that time, review stable issuer/subject identity linking, callback validation, cookie behavior and logout semantics. D45 selects CSRF protection for current cookie lifecycle operations independently of future SSO.

CSRF implementation boundary (D45): use a separate purpose-specific HMAC key and unambiguous message encoding, verify signatures and cookie/header equality in constant time, and reject missing/invalid/expired or incorrectly bound values before executing lifecycle actions. Never expose a refresh credential or raw session identifier in the readable CSRF token. Use a random nonce and bind authenticated tokens to a stable server session identity so refresh rotation/recovery does not invalidate CSRF across tabs. Refresh credentials remain HttpOnly; only the separate CSRF cookie is readable. Use host-only cookies with no parent Domain and explicit paths; SameSite=Lax follows D49; HTML delivery follows D47/D48. A pre-login token cannot automatically authorize an authenticated refresh/logout, and login must replace the anonymous binding. Future SSO callback correlation is deferred under D44.

Staff HTML CSRF initialization (D47): all full staff document loads, including direct navigation to protected SPA paths, must use the selected dynamic response boundary. Preserve valid anonymous/CSRF bindings rather than changing them on every tab load. For signed-out browsers, create a random HttpOnly anonymous binding cookie and a separate signed readable CSRF cookie. Successful login replaces the anonymous binding with the authenticated session binding. For an existing valid refresh session, validate it without consuming/rotating the credential and restore a missing or invalid CSRF cookie bound to that session. This lookup grants no resource access and never extends session deadlines. Enforce strict origin/Fetch Metadata policy for initialization and never cache personalized Set-Cookie HTML. Missing protection during SPA use requires a controlled full document reload with draft preservation where appropriate, not an unprotected refresh/logout bypass. Serving assets or HTML must not count as user activity. No HTML handler grants workspace authority before the Bearer session flow completes.

Cookie navigation behavior (D49): allow legitimate top-level GET navigation to staff HTML from external links while rejecting cross-origin state-changing API calls and cross-site embedded/subresource initialization. Do not require a same-origin Origin header on every document navigation, since it may be absent or identify the linking site; distinguish navigation from lifecycle mutations using verified original method/target and Fetch Metadata with a documented fallback. The gateway must forward trusted metadata accurately under D48. Lax cookies do not grant resource authority. Future cross-site POST SSO callbacks are out of current scope.

Pre-login expiry (D50): include signed issuance/expiry and anonymous-browser binding in validation; enforce the fixed 30-minute deadline even if the browser retains cookies. Reuse valid binding/CSRF protection on document loads without extending it. Expired pre-login protection returns 403 csrf_expired before credential authentication. Offer a clear reload action; preserve the entered email if appropriate, clear the password and require re-entry after refreshed document initialization. Do not repeatedly submit the old password, treat expiry as a failed password attempt, or alter an existing authenticated session solely because anonymous protection expired. Request-wide abuse counters still apply.

Browser persistence (D51): issue a persistent refresh cookie with Max-Age/Expires capped at the unchanged absolute session deadline; clear it on logout or confirmed expiry/revocation. Idle expiry is authoritative in PostgreSQL even if the browser retains the cookie until its absolute expiry. Reopening obtains CSRF protection through gateway/Go document initialization, then explicitly refreshes to obtain a memory-only access JWT. No browser-stored JWT, automatic credential replay, fresh login timestamp or activity renewal is implied by restoration.

Password-change transition (D52): verify current password, serialize against refresh/logout and recheck current account/session before committing. Password update, other-session revocation, current-session credential-generation change, replacement refresh hash and audit commit together. Reject prior-generation access JWTs immediately through server validation, not just JWT expiry. Invalidate prior refresh recovery records; password change is not a D43 refresh retry. Coordinate tabs to adopt the replacement authority and discard stale credentials; stable current-session binding can retain CSRF protection. Return credentials only after commit. If the response is lost, do not automatically replay a password mutation or claim rollback: explain the uncertain outcome and allow reauthentication using the updated password. Exact response/error recovery must be included in acceptance checks. Password change itself must not silently reset the absolute lifetime or bypass expiry.

Role switching with JWTs (D54): atomically change the current session active role and authority revision, and return a replacement access JWT plus current Session. Old-role JWTs cannot execute workspace requests after the switch. Refresh reads the current role/revision and cannot restore stale authority. Coordinate shared tabs, cancel old-scope requests and clear their private query caches; follow the agreed discard-or-stay prompt before switching with unsaved changes. Do not alter other sessions or reset session deadlines. A later employee role/assignment revocation still applies to all sessions using the revoked authority.

Keep internal locations inaccessible from visitor/staff public routes, strip spoofable forwarding headers, and disable auth-subrequest/document caching. Certificate sourcing/renewal must match organization-owned domains before deployment.

Internal initialization authentication (D65): use a dedicated purpose-bound gateway credential, independent of JWT signing, CSRF HMAC, recovery encryption and database credentials. Mount it through runtime secret configuration into only the relevant services; compare in constant time and reject missing/invalid credentials before initialization. Nginx overwrites any inbound internal-auth header and uses a private verified-TLS upstream with hostname/CA verification enabled. No certificate-verification bypass in production. Explicitly deny the initialization route on all public locations and redact header/cookie values in logs/errors. Provide a bounded operational key-rotation procedure and test invalid credentials, spoofed forwarding headers, expired/untrusted certificates and unintended public exposure. Exact certificate issuance and secret provisioning are deployment prerequisites, not invented credentials or authorization to provision infrastructure.

## 15. Request limits and deadline requirements

JSON body bound (D66): enforce actual bytes received rather than trusting Content-Length, including streamed/chunked requests. If compressed request bodies are supported later, bound decoded bytes as well; compression cannot bypass the cap. Preserve request ID and safe error structure where the rejecting layer can supply them; the frontend must also handle gateway-generated 413 responses without assuming JSON. Keep unsaved form data and do not retry oversize writes automatically. Boundary verification covers exactly 262,144 bytes, one byte over, and chunked bodies.

Upload request bounds (D67): align Nginx and Go multipart route limits so a valid 5 MiB file plus bounded metadata/framing fits. Independently enforce single-file count, per-file size, total actual streamed bytes and documented multipart fields; do not trust Content-Length or MIME headers alone. Reject excess with 413, remove partial temporary content, and never leave a usable attachment record/token for a rejected upload. Metadata must satisfy its own field limits rather than treating the full 1 MiB overhead allowance as arbitrary accepted fields. Verify boundary sizes, extra file parts, interrupted uploads and cleanup. Production upload enablement remains deferred.

Execution deadline (D68): derive a standard context with a 15-second budget at JSON handler entry after accepted body read and pass it through repositories/transactions and external calls. Configure database statement/lock timeouts within the remaining budget and avoid unbounded transaction retry loops. Do not treat a middleware response timeout as sufficient cancellation or leave detached handler writes running. With the selected Fiber implementation, verify context ownership and response-write safety against the supported version before coding. Nginx/client budgets allow the API deadline and bounded response overhead rather than expiring first by accident. Choose and document body-read/write/idle timeouts separately. Return a safe timeout error when the API can still respond; gateway timeout/non-JSON responses remain possible. Resolve uncertain submissions using the original reference rather than create a new booking.

Upload receive deadline (D69): verify absolute elapsed body-reception time at the public gateway boundary, including slow trickle traffic. Nginx client_body_timeout is an inter-read timeout and alone does not establish this total deadline. Select a supported, reviewed enforcement mechanism during implementation; if it requires a new gateway module or changes request buffering/streaming, surface that concrete change before adopting it. Coordinate Go read deadlines, bounded buffering/spooling, connection abort and temporary-file cleanup; downstream timers starting only after a fully buffered upload do not satisfy the ingress requirement. Verify a slowly trickled body cannot keep the request open past 60 seconds. Do not issue a token for incomplete/rejected uploads.

Upload processing (D70): begin a 15-second execution budget after full body reception, propagate it to validation/storage/database operations, and use bounded staging with atomic publication/link metadata. Check the deadline before publishing; avoid detached work that creates usable orphan tokens after a timeout response. Filesystem and DB writes are not a single transaction: define compensating deletion/orphan reconciliation and retain safe reference-based recovery for an uncertain commit. Do not issue a successful token before bytes and metadata are durably accepted. Verify storage failure, DB failure, deadline/commit races and retry with the original upload reference.

Streamed upload enforcement (D71): configure upload-only proxy_request_buffering off with an upstream protocol/configuration that does not silently buffer chunked bodies. Nginx replaces external timing headers with trusted original request timing; Go validates metadata only from the configured authenticated/trusted gateway connection and uses a conservative remaining receive budget, never a fresh 60 seconds after proxy delay. Keep header/body-read protection at ingress and bound backend connections/staging. Disable automatic upstream retry after body forwarding starts. Explicitly verify supported Fiber/fasthttp read deadline and multipart behavior against pinned versions; a context deadline alone cannot interrupt a blocked socket read. The 15-second post-receive processing budget starts only after body completion. Slow trickle, missing Content-Length, chunked transfer, client disconnect, invalid timing and partial-file cleanup are required acceptance cases. Ordinary JSON routes retain their own buffering policy.

Framework baseline (D72): target github.com/gofiber/fiber/v3. Current checked official documentation requires Go 1.26 or newer and the release listing identifies v3.7.0; these are review evidence, not an untested compatibility/security approval or automatic permission to install. Select/pin the supported toolchain and review middleware/driver/transitive compatibility before coding. Fiber handlers receive fiber.Ctx, while use cases/repositories receive the explicit standard context.Context obtained through c.Context() after deadline setup; never pass recycled transport context into durable work. Structural reference code remains v2 evidence and cannot be copied unchanged.

Toolchain baseline (D73): Go 1.27 is selected rather than sihp-be's older go.mod/Docker toolchains. Review the exact patch, module go/toolchain directives, build image digest and CI setup together; avoid accidental auto-download of an unreviewed different toolchain. Verify Fiber v3/GORM/PostgreSQL driver and observability/testing tools on the selected baseline. Keep version evidence dated and recheck before implementation; do not claim a passing build in this planning review.

Database version baseline (D74): PostgreSQL 18 is selected for new isolated databases, not an in-place upgrade of existing PostgreSQL data directories. Official support evidence lists 18.6 and support through November 2030; recheck/pin the reviewed minor and image before implementation. Validate PostgreSQL 18 image PGDATA/volume conventions rather than copy the template's PostgreSQL 16 mount assumptions. Disposable tests must exercise the actual selected major, migration role/runtime grants, resource-lock scheduling, outbox claims, limiter updates and refresh rotation under concurrency. Production upgrades/restores require a separately reviewed backup/rehearsal plan.

Schema evidence review: [diagram transcription and field register](BACKEND-SCHEMA-EVIDENCE-2026-11-11.md) now transcribes all 20 entities from a white-background rendering of the transparent source. D75 resolves role-assignment directorate as nullable metadata only. Access remains current role/permission/official-assignment based; no directorate-derived authority is introduced. Other semantic/cardinality/field-bound gaps remain under review before DDL/OpenAPI freeze.

Bcrypt credential boundary (D80): keep hashing behind a credential-verifier interface and store versioned encoded hashes privately, never passwords/encrypted recoverable passwords. Frontend byte counting must use UTF-8 bytes rather than ordinary text code-point limits; passwords containing non-ASCII characters reach 72 bytes sooner. Validate length before hashing and preserve password bytes without accidental field trimming. New-password/create over-limit validation is field-specific; login must retain generic credential-failure behavior. Work-factor calibration and hash concurrency must fit the chosen host and request deadlines; rate counters do not replace a bounded hash-work queue. No Argon2id implementation or legacy credential migration is selected.

Privacy fallback (D90): genuine public registration still requires an approved configured notice and explicit acknowledgment. Resolve an omitted privacyVersion to the current published server version in the booking transaction and retain that association; retries of an already committed reference return its existing outcome and never bind it to a newer notice. Store only necessary acknowledgment evidence with a retained published notice version; do not log public credential payloads. Missing notice configuration is unavailable, not an invented empty default. This fallback does not introduce a privacy-exception bypass or authorize production collection.
